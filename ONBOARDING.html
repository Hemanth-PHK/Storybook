1 What we're building

A reusable component library — one shared set of UI pieces (button, card, input…) that every screen of our e-learning platform is assembled from.

Instead of each of us building our own button on every page, we build each piece once, properly, and everyone reuses the same one. That gives us a consistent product and much faster screens later — like assembling Lego instead of moulding every brick by hand.

This is not throwaway This code ships into the real product and we build on it for months. So we build it properly — real, clean, production code. Quality over speed.

2 What is Storybook?

A separate workshop that runs beside our app, where we build and view one component at a time, on its own — without opening the whole website.

The analogy If the finished website is a car, Storybook is the workbench where you build and test each part — the headlight, the mirror — on its own before bolting it onto the car.

You build your component here and instantly see it, flip it through its states, and check it in every theme. The word to know is "story" — one example of a component in one state (a normal button, a disabled button…). Writing those stories is part of your job.

Good news — the setup is already done You don't need to configure Storybook, install it separately, or wire anything up. I've already completed all of that in the repository. Your only setup task is to connect to the repo and clone it — the exact steps are on the next section. After that, Storybook just runs.

3 Connect to the repository & clone

Follow these in order. By the end, Storybook will be running on your machine. If a step errors, message me before continuing — don't guess.

You need Git and Node.js 18+ installed. Check in your terminal:

node --version

If any says "command not found": install Git from git-scm.com and Node.js (LTS) from nodejs.org, then reopen your terminal.

Copy the repo URL. On the repo's GitHub page, click the green Code button and copy the HTTPS URL (looks like https://github.com/<org>/edtech-ui.git).

If Git asks you to sign in, use your GitHub username and a Personal Access Token as the password (GitHub → Settings → Developer settings → Personal access tokens). A normal password won't work for cloning.

Install dependencies. This reads the project and downloads everything it needs — including Storybook, automatically. Takes a minute; lots of text is normal.

Terminal — install

Start Storybook. It opens your browser at localhost:6006.

You're ready when The browser shows the Storybook interface and the terminal stays running (it won't return to the prompt — that's correct, leave it open). 5 The one concept that matters: themes

Click the 🎨 Theme dropdown and switch themes. The same button, no code changed:

Scholar Indigo
Teal Focus
Violet
Midnight

Everything recolored from one click. Every component you build must do this automatically.

Why our platform needs this — and why it decides how you code

Our e-learning platform has a dynamic theme-changing feature: a user clicks a palette icon in the corner and picks a theme, and the entire website instantly recolors to match. This isn't decoration — it's a real product requirement. And that one requirement is the reason we build every component a specific way. Here's the logic in order, so it clicks:

Because we want……the code must…
The whole site to recolor on one clicknever lock a color into a component
A component that never locks a colorrefer to a color by a name, not a value
A color referred to by nameuse a token like bg-primary

So tokens exist because the theme feature exists. If even one component hardcodes a color, that piece won't recolor when the user switches themes — it'll stay the wrong color while everything around it changes, and the feature visibly breaks. That's why "use tokens, never colors" isn't a style preference — it's what makes the product's headline feature actually work.

The mechanism — the empty box idea Think of bg-primary as an empty box labelled "primary color." Your component says "paint me with the primary color" and never knows which one it is. The theme fills the box: pick Ocean → the box gets teal; pick Midnight → the box gets indigo. Your component never changes — only what's in the box does. Switch theme → box gets a new color → every component using that token recolors together. One dropdown, whole site recolored. That's the feature, and tokens are how it's built.

6 The golden rule

The rule that governs everything you build
Never write a real color. Use a token.
No #hex. No bg-blue-500. Always a token name like bg-primary. If you type a # for a color — stop, and use a token instead.
✗ Breaks theming
bg-blue-500 text-white
bg-[#4f46e5]
style={{ background:"#fff" }}
✓ Follows the theme
bg-primary text-on-primary
bg-surface text-text
border border-border

Your color menu — the only color words you need

Need a color that's not here? Don't invent a hex. Ask me — a new token gets added to every theme first, then you use it.

7 The three files, in depth

Every component lives in its own folder, and inside are the same three files. They divide one job into three responsibilities. Here's what each one is for, and why it exists.

FileResponsibilityAnswers the question
Name.tsxThe component itselfWhat is it & how does it work?
Name.stories.tsxThe Storybook demosShow it in every state
index.tsThe public exportHow does the app import it?
Folder & naming convention Folder name = component name in PascalCase (Card, FormFields). The files inside match: Card.tsx, Card.stories.tsx, index.ts. Always these three names — an intern reading any folder knows instantly what's where. This sameness is a feature, not bureaucracy.

Card.tsxFile 1 · the component

What it is

The actual, real component that ends up on the website. Everything else in the folder exists to support this file. Read it as three parts, top to bottom:

Card.tsx — the reference pattern, annotated
// PART 1 — PROPS: the "settings menu" for this component.
// We extend the real HTML button so onClick, disabled, type… come free.
interface ButtonProps extends ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: "primary" | "secondary" | "danger";  // which look
  children: ReactNode;                              // the content inside
}

// PART 2 — STYLES: map each variant to TOKEN classes.
// This is where the golden rule lives — zero real colors.
const variantClasses = {
  primary:   "bg-primary text-on-primary hover:bg-primary-hover",
  secondary: "bg-surface text-text border border-border",
  danger:    "bg-danger text-on-primary",
};

// PART 3 — THE COMPONENT: take the settings, produce the element.
export function Button({ variant = "primary", children, ...props }: ButtonProps) {
  return (
    <button className={`px-4 py-2 rounded-lg ${variantClasses[variant]}`} {...props}>
      {children}
    </button>
  );
}

How to think about each part

Part 1 (props) declares what someone can customize — the variant, the content — plus everything a real HTML element already does. Part 2 (styles) is a lookup: "for this variant, use these token classes." Add or rename variants here. Part 3 (the component) is the function that glues settings + styles into the element on screen. When you build your component, you keep this three-part shape and change what's inside each part to fit your component.

Card.stories.tsxFile 2 · the demos

Why it exists

It doesn't create anything new — it shows the component from File 1 in Storybook, one state per "story." This file is what makes your component appear in the sidebar, and it's what satisfies "documented in Storybook."

Card.stories.tsx — annotated
// meta = introduces the component to Storybook
const meta: Meta<typeof Button> = {
  title: "Components/Button",   // its place in the sidebar
  component: Button,
  tags: ["autodocs"],           // auto-build a docs page
  args: { children: "Click me" }, // default for all stories
};
export default meta;

// each export below = ONE story = one state shown in Storybook
export const Primary = {};
export const Danger  = { args: { variant: "danger" } };
export const Disabled = { args: { disabled: true } };

Write one story per state your component can be in. That's how reviewers (and you) see every variation at a glance.

index.tsFile 3 · the export

What it solves

A tiny "front door." Without it, other files import from a long path (components/Card/Card). With it, they import cleanly from the folder (components/Card). One line does it:

index.ts — the whole file
export { Button } from "./Button";
export type { ButtonProps } from "./Button";

The summary to remember: build → display → export. .tsx builds it, .stories.tsx displays it, index.ts exports it. Every component, same three roles.

8 You open a blank IDE — now what?

This is the moment that feels scary. Here's the truth that removes the fear: you never start from a blank file. You copy the Button folder and change it.

1

In VS Code, find src/components/Button/. Copy the whole folder, paste it, rename the copy to your component (e.g. Card).

2

Rename the 3 files: Card.tsx, Card.stories.tsx, index.ts. Inside each, replace Button with Card.

3

Save. Look at Storybook — is Card in the sidebar? Click it. If it renders, you've proven the workflow.

4

Now build it for real — change what's inside the three parts to fit a card, using tokens only, and add a story per state.

The question in your head right now "The Button is written a certain way — do I copy that exact pattern, or write it my own way?"  → Copy the pattern. Always. Same file structure, same three parts, same token approach. Consistency across all eight components IS the deliverable — that's literally what the ticket asks for. You change the content, never the shape.

If any doubts come up while building — ping me anytime. 👍

9 Keep this / change this

The clearest way to think about building your component — what stays identical to Button, and what you make your own:

✓ Keep identical

  • The 3-file structure & their names
  • The three-part shape of the .tsx (props → styles → component)
  • Tokens for all colors — never hex
  • The stories format (meta + one export per state)
  • Typed props that extend the HTML element
  • Exporting via index.ts

✎ Change per component

  • The component name everywhere
  • The props — what YOUR component needs
  • The variants/styles in the lookup
  • The JSX it returns (a card's markup ≠ a button's)
  • The stories — your component's real states
  • The title in meta (e.g. "Components/Card")
Your self-check before review Open your component and flip through all themes with 🎨 Theme. If anything doesn't recolor, you hardcoded a color — find it, swap it for a token. That's your built-in bug detector.

11 "Done" checklist

Your component is finished when all of these are true. Check them before you ask for review.

  • Only token classes for color — zero #hex, zero bg-blue-500.
  • Has a stories file with a story for each state.
  • Keyboard-friendly — you can Tab to it and see a focus ring.
  • Props are typed — following how Button types its props.
  • Exported from its index.ts.
  • Recolors in every theme — verified with the 🎨 dropdown.

12 The rules that matter most

If you remember nothing else
Copy the Button. Use tokens, never colors.
Get those two right and you cannot fail your component. And one human rule: stuck for 20 minutes? Ask. That's expected, not a weakness — it's the fastest way for all of us to move.
